# ak-fetch 2.1.0 Benchmark Results

**Date:** 2026-08-09
**Dataset:** 100k records (`DATASET_SIZE=100k`, `testData/100k.ndjson`)
**Target:** real Mixpanel `/import` API
**Environment:** same machine, back-to-back runs (2.1.0 first, then main), no other load
**2.1.0 branch:** `release/2.1.0` @ post-C1-fix · suite duration **1.86 min**
**Baseline:** `main` (2.0.16) in a clean worktree · suite duration **2.07 min**

> **This document replaces an earlier version whose numbers and conclusions were wrong.**
> See [Corrections](#corrections-to-the-previous-version-of-this-document) at the bottom.

## Methodology caveats — read before quoting any number here

These are single measurements against a live third-party service, not a
controlled benchmark. Specifically:

- **N = 1 per profile.** Every cell in every table below is one run. There are
  no repetitions, no error bars, and no variance estimate. Differences under
  roughly 10% should be treated as indistinguishable from noise.
- **Live API.** All runs hit the real Mixpanel `/import` endpoint over the public
  internet. Server-side load, rate limiting, DNS, and network path all vary
  between runs and are not controlled for.
- **Run ordering is confounded with branch.** 2.1.0 ran first, then main, back to
  back — never interleaved and never randomised. Any drift in network or machine
  conditions over that window is indistinguishable from a branch effect.
- **Raw JSONs are not retained.** `benchmarks/results/` is gitignored and has
  been cleaned. The filenames are listed at the bottom for provenance, but the
  underlying data can no longer be re-examined; the tables here are all that
  survives.
- **`forceGC` was inert.** The harness ran without `--expose-gc`, so any profile
  setting `forceGC: true` (notably `Minimal Memory`) silently got no forced
  collection. The `bench:100k`/`bench:1m` scripts have since been fixed to pass
  the flag; the numbers below predate that fix.
- **"Peak memory" means peak heapUsed, not RSS.** See §3.

The throughput comparisons are large and consistent enough (+15-25%, in the same
direction across six independent profiles) to survive these caveats. Individual
memory cells are not.

## Correction 1: the main branch is NOT broken

The previous run of this benchmark reported that main failed 100% of tests with
`Invalid data format`, and speculated the cause was finding A1 (double-transform
corruption). **That was wrong.** `Invalid data format` is ak-fetch's *own*
`ValidationError`, thrown from `createDataStream` (`index.js`) when `data` is a
string that is neither an existing file path nor parseable JSON/JSONL:

```js
} else {
    throw new ValidationError('Invalid data format');
}
```

`testData/` is gitignored, so the freshly-created `main` worktree contained no
`100k.ndjson`. Every benchmark passed the path `./testData/100k.ndjson`, the file
did not exist, the string was not JSON, and ak-fetch rejected it before a single
byte hit the network. It was a **harness/data setup problem**, not a code defect.

Reproduced deliberately, then fixed by symlinking the datasets into the worktree:

```
--- PROBE A: missing dataset file ---
A: threw ValidationError -> "Invalid data format"

--- PROBE B: real request, 2000 records from 100k.ndjson (main branch) ---
dataset exists: true
reqCount: 1 rowCount: 2000 errors: 0
captured error bodies: []
responses sample: [ { "data": { "code": 200,
                                "num_records_imported": 2000,
                                "status": "OK" },
                      "status": 200, "statusText": "OK",
                      "url": "https://api.mixpanel.com/import?strict=1",
                      "method": "POST" } ]
```

Main imports records into Mixpanel successfully. With the datasets present, the
main benchmark suite completes with a 0.00% error rate on every test, exactly
like 2.1.0. There is no A1 corruption visible at the API level.

## Correction 2: pre-fix 2.1.0 was a throughput *regression*, not a win

The earlier 2.1.0 numbers (a flat ~10,000 records/sec at every concurrency level)
were measured on a build where `TaskPool.submit()` resolved on task *completion*
instead of acceptance, serializing every HTTP request in the library. Main's
older wave-based `run-queue` was slower than a continuous pool but still genuinely
concurrent, so the pre-fix 2.1.0 build was roughly **12x slower than main**.

The fix (`submit()` resolves on slot admission; `drain()` awaits completion) is
what the numbers below measure.

| Concurrency | pre-fix 2.1.0 (serialized) | main 2.0.16 | 2.1.0 (fixed) |
|-------------|---------------------------|-------------|---------------|
| 5           | 9,922 rec/s               | 42,012      | 45,149        |
| 40          | 9,740 rec/s               | 124,055     | 142,226       |

Isolated micro-verification of the pool itself (local server, 30ms latency,
20 requests, `batchSize: 1`, `concurrency: 10`):

| Build | peak concurrent | wall clock |
|-------|-----------------|------------|
| pre-fix | 1 | 678ms (serial floor is 600ms) |
| fixed   | 10 | 86ms |

### Investigating the `Minimal Memory` regression (finding I-2)

The 2.1.0 spec gate said "no memory regression tolerated", so the 79.0MB vs
46.4MB row was investigated locally against `test/helpers/local-server.js` —
100,003 records, 51 requests, the profile's exact settings (`batchSize: 2000`,
`concurrency: 3`, `storeResponses: false`, `maxResponseBuffer: 1`,
`forceGC: true`, `highWaterMark: 8192`), a fixed-latency local server, 20ms
`process.memoryUsage()` sampling, and `main` checked out in a parallel worktree.
Runs were interleaved main/2.1.0 to cancel drift. Means of 5 runs each, no
`--expose-gc` (i.e. faithful to how `npm run bench:100k` actually runs).

**Note:** The harness for this investigation was a discarded scratch script; the numbers below are single-machine observations and are not independently reproducible from the repo.

| metric | main | 2.1.0 | delta |
|---|---|---|---|
| peak heapUsed | 39.1MB | 54.0MB | **+38%** |
| avg heapUsed | 30.2MB | 33.2MB | +10% |
| peak RSS | 197.4MB | 185.4MB | **−6%** |
| peak external | 30.8MB | 21.6MB | **−30%** |
| throughput | 31,912 rec/s | 36,273 rec/s | **+14%** |

The heap regression reproduces (+38% locally vs +70% live, same direction, and
local main's 39.1MB is close to live main's 46.4MB). The throughput regression
does **not** reproduce — locally 2.1.0 is 14% *faster* on this profile, not 16%
slower. Three further measurements identify the cause:

1. **It is not queue depth.** Sweeping `maxTasks` across 3, 6, 12 and 25 (with
   `concurrency: 3`) left peak heap flat at 52MB in every arm. The new
   backpressure high-water mark is not holding extra batches resident.
2. **It is allocation rate.** Re-running both branches at a latency high enough
   that both are network-bound collapses the gap from +38% to +7% — main 41.4MB
   vs 2.1.0 44.4MB, inside run-to-run noise — and at that point 2.1.0's *average*
   heap is lower than main's (27.5MB vs 29.4MB).
3. **Collecting inverts the result.** With `--expose-gc`, so the profile's
   `forceGC: true` actually does something, 2.1.0 peaks at 45.1MB against main's
   57.2MB (means of 3 runs each) — 2.1.0 is the leaner branch.

So peak `heapUsed` on this profile is measuring how much garbage V8 tolerates
before collecting, and 2.1.0 generates that garbage 14% faster. The quantities
that reflect real memory cost — average heap, RSS, and external/ArrayBuffer
bytes — all moved in 2.1.0's favour. No library defect was found and no
config-mapping fix applies; see the "Known tradeoffs" entry in `CHANGELOG.md`
for the accepted waiver.

**A harness bug contributed.** The `Minimal Memory` profile sets `forceGC: true`,
but `index.js` guards it with `if (forceGC && global.gc)`, and `npm run
bench:100k` did not pass `--expose-gc` — so the profile's central knob was a
silent no-op and peak heap was left entirely to V8's discretion. The
`bench:100k` / `bench:1m` scripts now pass `--expose-gc`. **The tables in this
document were recorded before that change and are not retroactively corrected;
a live re-run is deferred.**

## 4. Connection pooling (finding B1)

| Branch | Pooling DISABLED | Pooling ENABLED | Gain | Avg req latency |
|--------|------------------|-----------------|------|-----------------|
| main 2.0.16 | 83,410 rec/s | 84,303 rec/s | **+1.1%** | 23.51 → 23.26ms |
| 2.1.0       | 79,499 rec/s | **108,389 rec/s** | **+36.3%** | 24.67 → 18.09ms |

This is the cleanest empirical confirmation of finding B1. On main, toggling
`enableConnectionPooling` changes throughput by 1.1% — i.e. nothing, because the
flag was a no-op and both arms used the same default dispatcher. On 2.1.0 the flag
moves throughput 36.3% and cuts average request latency by 26.7%, because the
undici `Agent` is now actually wired in.

## Verdict

- **main (2.0.16) works.** It imports data into Mixpanel with a 0% error rate and
  scales with concurrency. The earlier "main is completely non-functional" claim
  was an artifact of a missing dataset file in the test worktree.
- **2.1.0 is faster**, by roughly **+15% to +25%** on like-for-like configurations
  (peak 142,226 vs 124,055 rec/s at concurrency 40; 102,983 vs 85,400 rec/s at
  batch 2000). The whole suite runs in 1.86 min vs 2.07 min.
- **Connection pooling is the single biggest real improvement**: it went from a
  measured no-op (+1.1%) to a measured +36.3%.
- **The concurrency pool genuinely fixed a self-inflicted regression.** The value
  of the C1 fix is that it restores and exceeds main's concurrency, not that main
  lacked concurrency.
- **One regression to watch, downgraded on investigation:** the `Minimal Memory`
  profile recorded 79.0MB peak heap on 2.1.0 vs 46.4MB on main, at lower
  throughput. Local reproduction (§3) confirms a real but smaller peak-heap
  increase (+38%, not +70%), does not reproduce the throughput drop at all
  (locally 2.1.0 is 14% faster), and shows peak RSS and external bytes both
  *improving*. The peak-heap delta tracks allocation rate, not retention.
  Accepted as a tradeoff; memory-constrained users should still benchmark their
  own profile before upgrading.
- The correctness fixes (A1-A5, B1-B15, C1, C4) remain the primary reason to ship
  2.1.0. They are validated by the test suite, not by these benchmarks — these
  benchmarks only show that the fixes did not cost performance.

## Recommended production configuration

```javascript
const productionConfig = {
  batchSize: 2000,                 // 102,983 rec/s, 98% batch fill
  concurrency: 25,                 // 138,733 rec/s; 40 adds only ~2.5% more
  enableConnectionPooling: true,   // +36.3% and -26.7% latency (now real)
  keepAlive: true,
  retries: 3,                      // 100% success in resilience tests
  retryDelay: 1000,
  timeout: 60000,
  maxResponseBuffer: 10,
  storeResponses: false,
};
```

Expected: ~100,000-140,000 records/sec against Mixpanel `/import` with a 0% error
rate. Batches above 2000 are rejected by the API — do not raise `batchSize`
further.

### Reproducing the main baseline

`testData/` is gitignored, so a fresh worktree has no datasets. They must be
linked in or the whole suite fails with `Invalid data format`:

```bash
git worktree add /tmp/akf-main main
cp .env /tmp/akf-main/
ln -s "$PWD/testData/100k.ndjson" /tmp/akf-main/testData/100k.ndjson
ln -s "$PWD/testData/1m.ndjson"   /tmp/akf-main/testData/1m.ndjson
cd /tmp/akf-main && npm install && npm run bench:100k
```

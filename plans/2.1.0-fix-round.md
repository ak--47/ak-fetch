## C-1 (critical) — FIXED

`lib/form-data-handler.js:4` did `import { statSync, existsSync, openAsBlob } from 'fs'`.
`openAsBlob` landed in Node 19.8. ESM validates named imports at **link** time, so
this threw `SyntaxError: The requested module 'fs' does not provide an export named
'openAsBlob'` on **every Node 18.x** and took the whole module graph down — the
package was unloadable on its own stated minimum. The runtime feature guard inside
`appendFilePath()` never got a chance to run. The CJS dist was immune because
esbuild emits `__toESM(require('fs')).openAsBlob`, i.e. a property access.

Fix: namespace import plus destructure, so the missing export becomes `undefined`
instead of a link error, with the reason recorded at the site.

```js
import fs from 'node:fs';
const { statSync, existsSync, openAsBlob } = fs;
```

Verified empirically on real Node 18.20.8 (not simulated): `index.js`, `cli.js`,
`lib/form-data-handler.js` all import, and `cli.js --version`/`--dryRun` work from
a foreign cwd.

**Regression gate:** `test/integration/node18-esm-compat.test.js`, 14 tests. It is
a *source scan*, so it runs and fails correctly on any Node version, including the
Node 22 CI would use. It reads `index.js`, `cli.js` and every `lib/*.js`, parses
their static named imports, and fails if any names a post-18 `fs` export
(`openAsBlob` 19.8, `statfs`/`statfsSync` 19.6, `glob`/`globSync` 22.0). It
includes a vacuity guard (asserts it actually saw ≥12 sources and >0 imports, so
it can't pass by scanning nothing) and a specific test asserting `openAsBlob` is
still *used* and still *feature-guarded*. Mutation-tested by reintroducing the
bug — the test fails.

One wrinkle worth recording: the scanner initially flagged its own explanatory
comment, which contains the literal bad import as an example. Fixed with a
quote-aware `stripComments()` rather than by deleting the example.

## I-2 — WAIVED, with local measurements

Full write-up in `plans/2.1.0-bench-results.md` §3 and in CHANGELOG under
**Known tradeoffs**. Live benchmarks were **not** re-run (they hit the real
Mixpanel API). Everything below is local, against `test/helpers/local-server.js`.

Method: 100,003 records / 51 requests, the `Minimal Memory` profile verbatim
(`batchSize: 2000`, `concurrency: 3`, `storeResponses: false`,
`maxResponseBuffer: 1`, `forceGC: true`, `highWaterMark: 8192`), fixed-latency
local server, 20ms `process.memoryUsage()` sampling, `main` in a parallel
worktree at `e6edac3`, runs **interleaved** main/2.1.0 to cancel drift. Means of
5 runs each, no `--expose-gc` (faithful to how `npm run bench:100k` ran):

| metric | main | 2.1.0 | delta |
|---|---|---|---|
| peak heapUsed | 39.1MB | 54.0MB | **+38%** |
| avg heapUsed | 30.2MB | 33.2MB | +10% |
| peak RSS | 197.4MB | 185.4MB | **−6%** |
| peak external | 30.8MB | 21.6MB | **−30%** |
| throughput | 31,912 rec/s | 36,273 rec/s | **+14%** |

The memory half of the finding reproduces (+38% local vs +70% live, same
direction; local main's 39.1MB is close to live main's 46.4MB, which suggests the
repro is faithful). **The throughput half does not reproduce at all** — locally
2.1.0 is 14% faster on this profile, against the live report's 16% slower.

Three follow-ups locate the cause:

1. **Not queue depth.** `maxTasks` swept across 3, 6, 12, 25 at `concurrency: 3`
   left peak heap flat at 52MB in every arm. The new backpressure high-water mark
   is not holding extra batches resident. (This was my leading hypothesis and it
   is wrong.)
2. **Allocation rate.** Re-running both at a latency high enough that both are
   network-bound collapses the gap from +38% to +7% — 41.4MB vs 44.4MB, inside
   noise — and there 2.1.0's *average* heap is lower (27.5 vs 29.4MB).
3. **Collecting inverts it.** With `--expose-gc`, so `forceGC: true` actually
   fires, 2.1.0 peaks at 45.1MB against main's 57.2MB (3 runs each).

Conclusion: peak `heapUsed` on this profile measures how much garbage V8 tolerates
before collecting, and 2.1.0 makes garbage 14% faster because it *is* faster.
Every metric that reflects retained memory (avg heap, RSS, external) improved. No
library defect found, no config-mapping fix available, so: explicit waiver. The
absolute peak is well under the 512MB default `maxMemoryUsage`, and the profile
buys the suite-wide +15-25%. Live re-run deferred.

**Two supporting defects found and fixed en route:**

- `bench:100k` / `bench:1m` never passed `--expose-gc`, so `forceGC: true` was a
  silent no-op in the very profile named "Minimal Memory" — peak heap was left
  entirely to V8's discretion. Both scripts now pass it. Both harnesses already
  gate their "run with `--expose-gc`" tip on `global.gc`, so no text goes stale.
  Disclosed in the bench doc: recorded tables predate this and are **not**
  retroactively corrected. This change does not carry the waiver — the waiver
  stands on the measurements above regardless.
- The "peak" column in the memory table is `peakHeapUsed`, **not** peak RSS
  (`benchmarks/memory-test.js` line 130 and the line 263 summary). Now stated
  where it's read. This is what made the live number so easy to misread.

Scratch artifacts deleted: `/tmp/akf-mem-probe.mjs` removed, `/tmp/akf-main-mem`
worktree removed (`git worktree list` shows only the repo).

## I-4 — FIXED

CHANGELOG gained an honest paragraph under **Changed → Behavior Changes** for
`maxTasks`: old = wave size (queue up to `maxTasks`, pause the stream, drain to
zero, repeat); new = plain backpressure high-water mark on the continuous pool,
no drain-to-zero barrier. Two consequences stated: the pool never accepts more
than `concurrency` at once, so any `maxTasks > concurrency` can never fire —
which includes the shipped defaults (25 vs 10), making it inert for most users;
and `maxTasks: 0` now means "no backpressure" rather than "drain constantly."
Advice included: set it *below* `concurrency` to keep having an effect. It's
flagged as a behavior change to an otherwise-frozen field, with the reason (the
wave barrier caused the C1 sawtooth).

## M-2 — FIXED, plus a masked bug underneath it

`executeRequest`'s catch only looked at `error.code`. Native fetch wraps transport
failures as `TypeError: fetch failed` with the real error on `.cause`, and
dual-stack hosts nest further inside `AggregateError.errors[]` — so ECONNREFUSED
and ENOTFOUND fell through to generic `AkFetchError`.

Added a `resolveErrorCode()` walker (breadth-first over `.cause` and `.errors`,
cycle-guarded) and reordered the catch to check timeouts before network. undici's
`UND_ERR_BODY_TIMEOUT` / `UND_ERR_HEADERS_TIMEOUT` now map to `TimeoutError`.
Network codes were hoisted into an exported `NETWORK_ERROR_CODES` in
`lib/retry-strategy.js` so classification and `isNetworkError()` can't drift
apart; `isNetworkError()` also now reads `error?.cause?.code`.

**Masked bug found while writing the tests:** `getResponseBody()` did
`try { return response.json() } catch { return response.text() }`. `.json()`
consumes the stream *before* it parses, so the fallback could never run — it
always threw `Body is unusable: Body has already been read`, and that error
replaced whatever the real failure was. It was actively hiding the
`UND_ERR_BODY_TIMEOUT` this finding is about. Now reads text once, then
`JSON.parse`. (Nine unit-test mocks needed a `text` method added; real `Response`
objects have always had one.)

New `test/integration/error-classification.test.js`, 12 tests: closed port →
`NetworkError` (bare and via `AggregateError`), ENOTFOUND from a recorded real
rejection so no DNS is needed, trickling body → `UND_ERR_BODY_TIMEOUT`, silent
server → `UND_ERR_HEADERS_TIMEOUT`, AbortController deadline, invalid-JSON body
returns raw text, and retry agreement (refused connection retried 3× then
`RetryError` with a `NetworkError` `lastError`). The undici codes are isolated
from the client's own abort by pairing a short client `timeout` with a long
per-request one.

## M-7 — FIXED, and it was hiding a real CLI crash

- **cli-portability malformed `--headers`.** The old test asserted only the
  *absence* of one specific TypeError string — so it passed while the CLI printed
  its friendly warning and then died on a *different* one. Root cause in
  `cli.js`: when both `JSON.parse` attempts fail, `val` becomes `defaultVal`,
  which is `undefined` at most call sites, and `Object.keys(undefined)` throws
  `TypeError: Cannot convert undefined or null to object`. **Fixed the CLI**
  (null guard before `Object.keys`), then rewrote the test to assert the warning
  text actually appears, exit code 0, no TypeError of any kind, and that the dry
  run completed. Needed `spawnSync` rather than `execFileSync` — the warning goes
  to stderr, which `execFileSync` only returns when the process *fails*, and it
  no longer fails.
- **`delete-body` vacuous block.** Assertions were nested in `if (response.echo)`.
  The echo actually lives at `response.data.echo`, so that guard was *never* true
  and the block had never run a single assertion. Now unconditional, asserting
  status, method, and echo shape (`toMatchObject`, since the fixture carries a
  live `timestamp`).
- **fire-and-forget comparative claim.** Added a test running the same 20 records
  twice off one base config, once with `retries: null` and once with retries:
  equal `reqCount`, `responses` empty in the fire-and-forget arm, real status 200
  and `.data.echo` in the stored arm. Also replaced an `expect(null).toBe(null)`
  tautology with a real test that only an explicit `null` triggers the mode —
  `undefined` and `0` do not.

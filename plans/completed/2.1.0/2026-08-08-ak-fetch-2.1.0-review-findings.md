# ak-fetch 2.0.16 — Full Module Review (Findings)

Reviewed: `index.js`, `lib/*` (all 9 modules), `cli.js`, `types.d.ts`, `package.json`, test suite (362 passing), README claims.
Method: full source read + empirical verification of every suspected bug against a live local HTTP server on Node v24.

**Headline:** the library works for its primary daily-driver path (JSON arrays/JSONL → batched POSTs with idempotent-or-no transforms), which is why it has "worked for years." But several documented features are silently broken or lying, and the HTTP layer predates Node's native fetch — the entire connection-pooling subsystem is a no-op.

---

## A. Confirmed bugs — empirically reproduced

### A1. `transform` is applied TWICE to every record (data corruption)
- Where: [index.js:990-1009](../index.js#L990-L1009) applies transform per-item in the stream loop; then `addBatchToQueue` spreads the full config (including `transform`) into `requestConfig`, and [http-client.js:156-161](../lib/http-client.js#L156-L161) applies it AGAIN to the batch.
- Repro: 2 items, `transform: (i) => ({...i, n: i.n + 10})` → transform called **4 times**, server received `n: 21` for input `n: 1` (expected `11`).
- Why tests miss it: every transform in the test suite is idempotent (`item.transformed = true`).
- Impact: any non-idempotent transform (counters, timestamps-offsets, appends) silently corrupts payloads. `clone` is also applied twice (wasted double JSON roundtrip).

### A2. `.json` file input crashes (`require` in ESM)
- Where: [index.js:824](../index.js#L824) — `require('fs').readFileSync(...)` inside an ES module.
- Repro: `data: './file.json'` → `ReferenceError: require is not defined`.
- Impact: the documented "file path to JSON" input mode has never worked in the ESM build.

### A3. `retries: 0` performs 4 attempts
- Where: [retry-strategy.js:54](../lib/retry-strategy.js#L54) — `this.maxRetries = options.maxRetries || 3` (`0 || 3 === 3`).
- Repro: failing server + `retries: 0` → **4 attempts** per request.

### A4. `retries: null` (fire-and-forget) performs 4 attempts
- Where: [index.js:723](../index.js#L723) / [index.js:924](../index.js#L924) — `retries: config.retries ?? 3` maps `null → 3`; retry-strategy `||` would do the same.
- Repro: failing server + `retries: null` → **4 attempts**.
- Impact: "fire-and-forget for max performance" mode actually retries with backoff — up to 4× the traffic and latency. Only the `storeResponses: false` half of the feature works.

### A5. Multipart file upload is completely broken
- Where: [http-client.js:179-185](../lib/http-client.js#L179-L185) passes a `form-data` (npm) Node stream as `body` to native fetch. undici rejects stream-ish bodies without `duplex: 'half'` and doesn't understand the `form-data` stream type.
- Repro: `headers: {'Content-Type': 'multipart/form-data'}` + `{file: './x.txt'}` → `Request failed: fetch failed` on every attempt.
- Why tests miss it: unit tests only test `FormDataHandler` in isolation; the "multipart" integration tests only check curl/dry-run string generation.

## B. Confirmed bugs — static (code-level certainty)

### B1. Connection pooling is a complete no-op (the big perf lie)
- Where: [http-client.js:33-46](../lib/http-client.js#L33-L46) builds `node:http/https` Agents and passes `agent` + `timeout` in fetch options ([http-client.js:219-227](../lib/http-client.js#L219-L227)). Native fetch (undici) **ignores both keys** — they are node-fetch options.
- Consequence: `enableConnectionPooling`, `keepAlive`, `maxSockets`, `maxFreeSockets`, `freeSocketTimeout`, and `rejectUnauthorized` do nothing. You get undici's default global dispatcher for everything. `getStats()` socket counts always read 0.
- Bonus: `undici` is declared in package.json dependencies and **never imported**.

### B2. Multiple `Set-Cookie` headers are collapsed
- Where: [http-client.js:238-241](../lib/http-client.js#L238-L241) — `Object.fromEntries(response.headers.entries())` comma-joins repeated `set-cookie` values before handing to tough-cookie. Multi-cookie sessions parse wrong. Fetch spec provides `response.headers.getSetCookie()` for exactly this.

### B3. 429 responses never consume the body
- Where: [http-client.js:244-249](../lib/http-client.js#L244-L249) throws `RateLimitError` without reading the body → undici keeps the connection reserved until GC. Under sustained rate-limiting this bleeds sockets; error also lacks the response body for debugging.

### B4. Case-sensitive header handling
- Where: [http-client.js:140](../lib/http-client.js#L140), [165](../lib/http-client.js#L165), [179](../lib/http-client.js#L179), [188](../lib/http-client.js#L188) — literal `'Content-Type'` / `'User-Agent'` key lookups. A user passing `'content-type': 'application/x-www-form-urlencoded'` gets the JSON code path plus a duplicate `Content-Type` header.

### B5. Latent instant-abort timeout
- Where: [http-client.js:110-125](../lib/http-client.js#L110-L125) — `executeRequest` destructures `timeout` with no default; `request()` defaults it but spreads the *original* config to `executeRequest`. Any call path where config lacks `timeout` → `setTimeout(abort, undefined)` → abort after ~1ms. Currently masked because `setDefaults()` always sets it; one refactor away from a prod fire.

### B6. Body reads are not covered by the timeout
- Where: [http-client.js:328-341](../lib/http-client.js#L328-L341) — `clearTimeout` fires in `finally` once headers arrive; a server that trickles the body stalls forever.

### B7. `batchSize: 0` contradicts its documentation
- Docs (README, CLI, types): "0 disables batching" (send everything as one request). Actual: `batch.length >= 0` is always true → **every record is sent as its own request**. The exact opposite of documented intent.

### B8. CLI reads `./package.json` from the CWD
- Where: [cli.js:9](../cli.js#L9). `npx ak-fetch` from any directory without a package.json → crash; with an unrelated package.json → wrong version banner.

### B9. CLI `parse()` references `this.verbose` in module scope
- Where: [cli.js:437](../cli.js#L437). `this` is `undefined` in ESM → passing malformed JSON for `--headers` throws `TypeError: Cannot read properties of undefined` from inside the error handler instead of the friendly message.

### B10. `engines: node >=16` is false
- Native `fetch` (used unconditionally) doesn't exist on Node 16. Module throws `fetch is not defined` at first request. Practical floor is 18 (and `Headers.getSetCookie` needs 18.14+).

### B11. `CircularBuffer(0)` corrupts itself
- Where: [circular-buffer.js:68-84](../lib/circular-buffer.js#L68-L84) — `maxResponseBuffer: 0` → `% 0` → `NaN` indexes, silent storage breakage. Should mean "store nothing."

### B12. Logger writes ANSI cursor codes to non-TTY streams
- Where: [logger.js:226-227](../lib/logger.js#L226-L227) etc. — `readline.cursorTo/clearLine` without an `isTTY` guard. Visible today: `[1G[2K` garbage throughout CI/vitest output and any piped logs.

### B13. `executeSingleRequest` reports `duration: 0` always
- Where: [index.js:746-748](../index.js#L746-L748) — `startTime = endTime`. Every `noBatch` result lies about timing.

### B14. Multi-config stats are self-inconsistent
- Where: [index.js:339-362](../index.js#L339-L362) — logs `rowCount: reqCount` but returns `rowCount: totalCount`; multi-config `verbose` defaults **true** while single-config defaults **false**.

### B15. CLI `batch_size` default is 2; library and README say 1
- Where: [cli.js:56](../cli.js#L56). Almost certainly a typo; CLI and programmatic runs behave differently out of the box.

## C. Design & performance issues (no behavior lie, just money on the table)

### C1. Wave-based concurrency (sawtooth throughput)
- Where: [index.js:1027-1049](../index.js#L1027-L1049). RunQueue only starts work when `.run()` is called. Tasks accumulate until `maxTasks` (25) queue up, then the code **drains the entire queue to zero** while the stream is paused, then builds the next wave. Concurrency graph is a sawtooth: 10 → 0 → 10 → 0. The tail of every wave runs below full concurrency, and stream reading doesn't overlap the final drain.
- Fix direction: continuous semaphore (p-limit pattern, ~30 lines, zero deps) — request N+1 starts the instant any of the N in flight completes; `maxTasks` becomes a real high-water backpressure mark. Also removes the `run-queue` dependency and the vestigial `stream.pause()/resume()` calls (meaningless under `for await`).

### C2. Dead dependencies shipped to every consumer
- `fetch-retry` — never imported anywhere.
- `readline`, `querystring` (npm packages) — Node builtins shadow both; the npm packages are dead weight (npm `querystring` is deprecated; npm `readline` is an abandoned junk package).
- `json-stable-stringify` — imported in presets.js, never called.
- `undici` — declared, never imported (becomes real in 2.1.0).
- `form-data` — removable once multipart moves to native FormData.
- `run-queue` — removable with C1.

### C3. Unused StreamProcessors surface
`createBatchTransform`, `createBackpressureTransform`, `createRateLimitTransform`, `createTeeStream`, `getUniqueKeys` are not referenced by the engine. Internal-only (not exported from package root), so pruning is safe; unit tests cover some — prune opportunistically.

### C4. Misc
- `User-Agent: ak-fetch/1.0` hardcoded — wrong major version.
- `sanitizeConfig` masks only `authorization`, `cookie`, `x-api-key`.
- `types.d.ts` documents `verbose` default as `true`; library default is `false`.
- `dotenv.config()` runs as a side effect of importing the library (mutates consumer env). Long-standing behavior — keep, but worth knowing.
- Presets mutate records in place when `clone: false` (default) — documented-ish via `clone`, leaving as designed.
- RetryError message (`All 3 retry attempts failed`) hides the underlying cause; `lastError` carries it but the message should too.

## D. Why the test suite (362 passing) missed all of this

1. Transforms in tests are all idempotent → A1 invisible.
2. No test asserts **attempt counts** against a failing server → A3/A4 invisible.
3. Multipart tests assert dry-run/curl string output, never a real request → A5 invisible.
4. No test loads a `.json` file path → A2 invisible.
5. Pooling tests assert config plumbing (`getStats()` shape), not socket reuse → B1 invisible.
6. Everything runs on one Node version with defaults that mask latent paths (B5).

The 2.1.0 plan adds a regression test for every lettered finding above before touching the code that fixes it.

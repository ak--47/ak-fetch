### N-1 — scanner false negative (Minor)

The import matcher is
`/(?:^|[\s;}])(?:import|export)\s+([\s\S]*?)\s*from\s*['"]([^'"]+)['"]/g`.
The lazy `[\s\S]*?` means an `export` statement appearing *textually before* an fs
named import swallows it: the match begins at the earlier `export`, runs to the
later `from 'fs'`, and `clause.match(/\{([\s\S]*?)\}/)` picks up a function/class
body instead of the import clause. Demonstrated:

```
input : export function foo() { return { a: 1 }; }
        import { openAsBlob } from 'fs';
result: []            ← should have been a violation
```

**Currently unreachable** — I checked all 12 shipped sources; in every one the first
`export` token comes after the last `import … from`. But `lib/retry-strategy.js` now
has `export const NETWORK_ERROR_CODES` at line 26, so any fs import added below it in
that file would silently escape the scan. Second, narrower point: the gate covers
only `fs`. The same *class* of link-time break via `node:util` (`styleText`, 20.12),
`node:stream`, etc. is not guarded — the test name says "Node 18 ESM link-time
compatibility" but the assertion is fs-only. Both are cheap to tighten later; neither
blocks publish, since the exact regression it exists to prevent is caught.

### N-2 — vacuity guard is a tripwire on file count (Minor)

`expect(sources.length).toBeGreaterThanOrEqual(12)` equals today's count exactly
(index + cli + 10 `lib/*.js`). Deleting or merging any lib module fails this test with
a message about the scan seeing nothing, which is not what happened. A guard on
"index.js and cli.js are present and lib/ is non-empty" would be less fragile.

### N-3 — invalid-JSON responses now succeed silently (Minor)

Pre-fix, a 200 response with `content-type: application/json` and a non-JSON body
threw (`Body is unusable: Body has already been read`), became a generic
`AkFetchError`, and was counted in `result.errors`. Post-fix it resolves with the raw
string in `result.data` and status 200 — confirmed by the new test, which fails on
the pre-fix tree. This is the *intended* semantics (the original code plainly meant
`try json, fall back to text`) and the CHANGELOG describes the mechanism, but it sits
under **Fixed** with no "Changed"/migration line. A consumer that leaned on
malformed-JSON responses surfacing as errors will now see them as successes carrying
a string payload. Worth one migration bullet; not worth blocking.

### N-4 — §3 is as unreproducible as what it corrects (Minor)

`plans/2.1.0-bench-results.md` §3 states the local table holds *"the only memory
numbers in this document that are backed by a recorded table."* Per
`plans/2.1.0-fix-round.md:152-154`, the harness (`/tmp/akf-mem-probe.mjs`) and the
`main` comparison worktree were both deleted. So §3's numbers are exactly as
un-re-examinable as the live tables the new Methodology-caveats section criticizes,
and the caveat is not repeated there. Nothing appears fabricated — the internal
consistency is good and the direction matches the live run — but the framing gives §3
an authority it hasn't earned. One sentence ("harness not retained; a re-run requires
rebuilding the probe") would close it. This is what keeps M-6 at PARTIALLY.

### N-5 — wider retry surface, no idempotency caveat (Minor)

M-2's fix means `ECONNRESET`, `EHOSTUNREACH`, `EAI_AGAIN`, `UND_ERR_BODY_TIMEOUT`,
etc. now reach `NetworkError`/`TimeoutError` and are therefore retried by default
(`retryOnNetworkError: true`). For a bulk-ingest client, retrying a POST that failed
*after* the server accepted the batch produces duplicate records. The CHANGELOG does
say "connection failures and body/header deadlines are now retried by default, as
`retryOnNetworkError: true` always claimed", which is the honest framing, and the
pre-existing AbortController-timeout path already had this property — so the
increment is genuinely small. Still, neither README nor CHANGELOG anywhere notes that
retries are not idempotency-safe. Worth a line for an analytics-ingest audience.

### Adversarially checked, nothing found

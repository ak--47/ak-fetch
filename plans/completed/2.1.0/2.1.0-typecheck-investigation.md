## Error 1: Buffer → BlobPart Type Mismatch

### Location
`lib/form-data-handler.js:70`

### Full Error
```
TS2322: Type 'Buffer' is not assignable to type 'BlobPart'.
  Type 'Buffer' is not assignable to type 'ArrayBufferView<ArrayBuffer>'.
    Types of property 'buffer' are incompatible.
      Type 'ArrayBufferLike' is not assignable to type 'ArrayBuffer'.
        Type 'SharedArrayBuffer' is not assignable to type 'ArrayBuffer'.
          Types of property '[Symbol.toStringTag]' are incompatible.
            Type '"SharedArrayBuffer"' is not assignable to type '"ArrayBuffer"'.
```

### Current Code
```javascript
const blob = typeof openAsBlob === 'function'
    ? await openAsBlob(filePath, { type })                       // Node ≥19.8: lazy, streams from disk
    : new Blob([await readFile(filePath)], { type });            // Node 18 fallback: buffered
```

Line 70: `new Blob([await readFile(filePath)], { type })`

### Root Cause
`fs/promises.readFile()` returns a `Buffer`, which extends `Uint8Array` but has a `.buffer` property typed as `ArrayBufferLike` (union of `ArrayBuffer | SharedArrayBuffer`). TypeScript's `BlobPart` type requires `ArrayBufferView<ArrayBuffer>`, which means the `.buffer` property must be exactly `ArrayBuffer`, not `SharedArrayBuffer`.

This is a **TypeScript strictness issue** — the code works perfectly at runtime (Buffer is accepted by Blob constructor), but TS's generic constraint on `ArrayBufferView<T>` is stricter than the actual Blob specification.

### Verification
Tested in `/tmp/test-error1-buffer.js`:
- `new Blob([buffer])` — works at runtime ✅
- `new Blob([new Uint8Array(buffer)])` — works at runtime AND typechecks ✅
- `new Blob([buffer.buffer])` — works at runtime ✅

### Recommended Fix: CODE FIX
**Wrap Buffer in `new Uint8Array()` for explicit BlobPart compliance**

```javascript
// Line 70 - replace
: new Blob([await readFile(filePath)], { type });

// with
: new Blob([new Uint8Array(await readFile(filePath))], { type });
```

**Why this fix:**
1. ✅ **Real improvement**: Makes the type explicit and semantically clearer
2. ✅ **Zero runtime cost**: `new Uint8Array(buffer)` when buffer is already a Buffer/Uint8Array creates a view, not a copy
3. ✅ **Fixes the type error**: `Uint8Array` is unambiguously `ArrayBufferView<ArrayBuffer>`
4. ✅ **Future-proof**: Works with any Node.js version's Buffer implementation

**Alternatives considered:**
- JSDoc `@ts-ignore` — hides the issue, doesn't improve code
- Casting with `/** @type {BlobPart[]} */` — less clear than the fix
- Accessing `.buffer` directly — semantically wrong (we want the typed array, not the raw buffer)

## Error 2: FormData Not Assignable to String Parameter

### Location
`lib/http-client.js:224`

### Full Error
```
TS2345: Argument of type 'string | FormData' is not assignable to parameter of type 'string'.
  Type 'FormData' is not assignable to type 'string'.
```

### Current Code
```javascript
// Line 224 - inside executeRequest()
if (dryRun === 'curl') {
    return this.generateCurlCommand(requestUrl, method, requestHeaders, requestBody);
}

// Lines 395-414 - generateCurlCommand JSDoc
/**
 * Generate curl command for dry run
 * @param {URL} url - Request URL
 * @param {string} method - HTTP method
 * @param {Object} headers - Request headers
 * @param {string} body - Request body  ← ONLY EXPECTS STRING
 * @returns {string} Curl command
 */
generateCurlCommand(url, method, headers, body) {
    let curlCommand = `curl -X ${method} "${url}"`;
    
    Object.entries(headers).forEach(([key, value]) => {
        curlCommand += ` \\\n  -H "${key}: ${value}"`;
    });

    if (body) {
        curlCommand += ` \\\n  -d '${body}'`;  ← ASSUMES STRING
    }

    return curlCommand;
}
```

### Root Cause
`requestBody` is set to different types based on `Content-Type`:
- Line 200: `application/x-www-form-urlencoded` → `querystring.stringify()` → **string**
- Line 204: `multipart/form-data` → `createFormData()` → **FormData**
- Lines 214/216: JSON (default) → `JSON.stringify()` → **string**

When `dryRun === 'curl'`, the code passes `requestBody` (which could be `FormData`) to `generateCurlCommand()`, but the function's JSDoc says it expects `string`.

**Reality check**: curl CAN'T represent multipart form data in a simple `-d` flag — it needs `-F` flags per field, and FormData in JS is opaque (can't iterate without consuming). The current implementation would crash at runtime if you tried `dryRun: 'curl'` with FormData body.

### Verification
Tested in `/tmp/test-error2-formdata.js`:
- Passing FormData to string parameter fails typecheck ❌
- Updating JSDoc to `@param {string | FormData}` and handling both types works ✅

### Recommended Fix: CODE FIX
**Update `generateCurlCommand` to handle FormData explicitly**

```javascript
/**
 * Generate curl command for dry run
 * @param {URL} url - Request URL
 * @param {string} method - HTTP method
 * @param {Object} headers - Request headers
 * @param {string | FormData} body - Request body (FormData rendered as placeholder)
 * @returns {string} Curl command
 */
generateCurlCommand(url, method, headers, body) {
    let curlCommand = `curl -X ${method} "${url}"`;
    
    Object.entries(headers).forEach(([key, value]) => {
        curlCommand += ` \\\n  -H "${key}: ${value}"`;
    });

    if (body) {
        // Handle both string and FormData
        const bodyStr = typeof body === 'string' ? body : '[FormData - use multipart/form-data]';
        curlCommand += ` \\\n  -d '${bodyStr}'`;
    }

    return curlCommand;
}
```

**Why this fix:**
1. ✅ **Real bug fix**: The current code would fail at runtime with FormData in curl mode
2. ✅ **Documents truth**: The JSDoc now matches reality (FormData IS passed here)
3. ✅ **Degrades gracefully**: Shows `[FormData]` placeholder instead of crashing
4. ✅ **Type-safe**: Narrows the union before stringification

**Alternatives considered:**
- Type narrowing at call site (line 224) — pushes the problem upstream, doesn't fix the function
- JSDoc `@ts-expect-error` at call site — hides a real bug
- Full FormData serialization to curl `-F` flags — out of scope, complex, low value

## Error 3: Property 'stats' Does Not Exist on Agent

### Location
`lib/http-client.js:426`

### Full Error
```
TS2339: Property 'stats' does not exist on type 'Agent'.
```

### Current Code
```javascript
// Lines 416-438 - getStats()
/**
 * Get HTTP client statistics.
 *
 * NOTE: undici 6's `Agent` exposes no `.stats` property, so `sockets` and
 * `freeSockets` are always 0. The keys are kept for shape compatibility
 * with pre-2.1.0 consumers — do not read them as real socket counts.
 *
 * @returns {Object} Statistics
 */
getStats() {
    const s = this.dispatcher.stats ?? {};  // ← LINE 426
    const agentStats = {
        maxSockets: this.options.maxSockets,
        maxFreeSockets: this.options.maxFreeSockets,
        sockets: s.connected ?? 0,
        freeSockets: s.free ?? 0
    };
    return {
        httpsAgent: agentStats,
        httpAgent: agentStats,
        retryStrategy: this.retryStrategy.getStats(),
        cookieJar: this.cookieJar.getStats()
    };
}
```

### Root Cause
**undici 6.x Agent has NO `stats` property** — not in the TypeScript definitions, not in the runtime implementation. 

The JSDoc comment at lines 419-422 **already documents this**:
> NOTE: undici 6's `Agent` exposes no `.stats` property, so `sockets` and `freeSockets` are always 0. The keys are kept for shape compatibility with pre-2.1.0 consumers — do not read them as real socket counts.

The code uses nullish coalescing (`?? {}`) to handle the missing property gracefully, returning zeros for `connected` and `free`. This is **intentional defensive coding** — the comment says the ruling was to keep the shape but not claim real stats.

### undici 7 Analysis
**Could upgrading to undici 7 fix this?**

❌ **NO — undici 7 breaks compatibility**

- **Requirement**: undici 7.0.0+ requires Node.js >=20.18.1
- **Project requirement**: Node.js >=18.17 (see package.json engines)
- **Impact**: Upgrading would break CJS build for Node 18 users
- **Stats in undici 7**: Checked type definitions — Agent STILL has no `stats` property in 7.x

**Conclusion**: Upgrading to undici 7 would NOT fix the error and WOULD break Node 18 support.

### Verification
Tested in `/tmp/verify-fix3-noImport.js`:
- `dispatcher.stats ?? {}` works at runtime (returns `{}`) ✅
- `@ts-expect-error` suppresses type error ✅
- Bracket notation `dispatcher['stats']` avoids type error ✅

### Recommended Fix: @ts-expect-error WITH EXPLANATION
**Document that the missing property is expected and handled**

```javascript
getStats() {
    // @ts-expect-error - undici 6 Agent has no stats property; nullish coalescing provides shape-compatible fallback (see JSDoc above)
    const s = this.dispatcher.stats ?? {};
    const agentStats = {
        maxSockets: this.options.maxSockets,
        maxFreeSockets: this.options.maxFreeSockets,
        sockets: s.connected ?? 0,
        freeSockets: s.free ?? 0
    };
    return {
        httpsAgent: agentStats,
        httpAgent: agentStats,
        retryStrategy: this.retryStrategy.getStats(),
        cookieJar: this.cookieJar.getStats()
    };
}
```

**Why this fix:**
1. ✅ **Documents truth**: The property doesn't exist, and that's fine
2. ✅ **Preserves runtime behavior**: Nullish coalescing already handles it
3. ✅ **Links to existing JSDoc**: The longer explanation is in the function comment
4. ✅ **No breaking changes**: Doesn't change public API shape
5. ✅ **Type-safe**: Tells TypeScript this is intentional, not a mistake

**Alternatives considered:**
- **Bracket notation** `dispatcher['stats']` — avoids error but looks like a hack, loses the semantic intent
- **JSDoc type cast** — more verbose than `@ts-expect-error`, same effect
- **Upgrade undici** — breaks Node 18 support, doesn't fix the error anyway
- **Install @types/node** — not needed (using built-in types), wouldn't help (error is from undici types)

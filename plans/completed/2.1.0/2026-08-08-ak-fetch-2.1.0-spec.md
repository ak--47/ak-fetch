# ak-fetch 2.1.0 — Design Spec

**Companion docs:** [review findings](./2026-08-08-ak-fetch-2.1.0-review-findings.md) (the "why"), [implementation plan](./2026-08-08-ak-fetch-2.1.0-implementation-plan.md) (the "how").

## Goal

Make ak-fetch actually deliver what its README already promises — real connection pooling, correct retry semantics, working multipart, smooth max-throughput concurrency — **without changing the external API**. Fix every confirmed bug from the review. Same config in, same result shape out, faster and correct.

## Non-goals (YAGNI guard)

- No new config options. No renamed options. No new exports.
- No HTTP/2, no proxy support, no request signing — not in this release.
- No new vendor presets.
- No streaming-response bodies to disk.
- No rewrite of the logger beyond TTY correctness.
- `dotenv` side-effect on library import stays (long-standing observable behavior).

## Constraints

1. **Public API frozen:** default export `akFetch(config | config[])`, the 9 error classes, `BatchRequestConfig` fields and semantics, `Result` shape, all CLI flags.
2. **Behavior changes allowed only where current behavior contradicts the documentation** (that's a bug fix, not an API change): `retries: 0`, `retries: null`, `batchSize: 0`, `.json` file input, multipart, transform-once.
3. **Node floor becomes `>=18`** in `engines`. Not a real break: the module already throws `fetch is not defined` on 16/17. Guard newer APIs (`Headers.getSetCookie` 18.14+, `fs.openAsBlob` 19.8+) with feature checks so plain 18.0 still works.
4. Tests first: every fix lands with a regression test that fails on 2.0.16.
5. Coverage threshold stays ≥ 80%.

## Design

### 1. HTTP engine: undici dispatcher (fixes B1, B3, B5, B6, B2)

Replace the dead `node:http/https` Agents with a real undici `Agent` passed as `dispatcher` to fetch — the one mechanism native fetch actually honors. `undici` moves from "declared, unused" to the core engine dependency (pinned to the version Node bundles semantics we test against).

```js
// lib/http-client.js (concept)
import { Agent } from 'undici';

this.dispatcher = new Agent({
    connections: this.options.maxSockets,          // per-origin socket cap (concurrency * 2, as today)
    pipelining: this.options.keepAlive ? 1 : 0,    // pipelining 0 = no keep-alive → pooling "off"
    keepAliveTimeout: this.options.freeSocketTimeout,
    headersTimeout: this.options.timeout,
    bodyTimeout: this.options.timeout,             // fixes "body read escapes the timeout"
    connect: { rejectUnauthorized: this.options.rejectUnauthorized }
});

const response = await fetch(url, { method, headers, body, signal, dispatcher: this.dispatcher, redirect: 'follow' });
```

- `enableConnectionPooling: false` → `pipelining: 0` dispatcher (connection-per-request), keeping the option meaningful.
- Whole-request deadline stays an `AbortController`; `timeout` resolved as `config.timeout ?? this.options.timeout` **inside** `executeRequest` (kills the latent instant-abort).
- 429 path consumes the response body before throwing and attaches it to `RateLimitError.body`.
- Cookie extraction uses `response.headers.getSetCookie()` (feature-checked), and cookie processing is skipped entirely when `enableCookies` is false.
- Header handling goes case-insensitive via two small helpers (`getHeader(headers, name)` / `deleteHeader(headers, name)`).
- `destroy()` destroys the dispatcher. `getStats()` keeps its shape but reports dispatcher stats (`connected`, `pending`, `running`, `size` mapped onto the existing keys — shape-compatible, values now real).
- `User-Agent` default becomes `ak-fetch/2` (was `ak-fetch/1.0`).

**Alternative considered:** keep node-fetch-style Agents by switching to `undici.request` directly. Rejected — fetch keeps redirects/decompression/spec behavior for free and the dispatcher option is the designed extension point.

### 2. Concurrency: continuous pool, not waves (fixes C1)

New internal module `lib/concurrency.js` (~40 lines, zero deps) with a `TaskPool`:

```js
class TaskPool {
    constructor(concurrency, maxPending = Infinity)
    async submit(fn)   // starts fn when a slot frees; awaits (backpressure) while pending >= maxPending
    async drain()      // resolves when everything submitted has settled
}
```

- `processDataStream` and `processMultipleConfigs` drop `run-queue` for `TaskPool`.
- `concurrency` means what it always meant: max in-flight requests — but now the pool refills continuously instead of draining to zero every 25 tasks.
- `maxTasks` keeps its documented meaning ("max queued tasks before pausing stream"): `submit()` awaiting *is* the stream pause, via `for await` backpressure. The explicit `stream.pause()/resume()` calls and queue-rebuild dance are deleted.
- Task bodies keep their own try/catch (they already do), so pool promises never reject and error accounting is unchanged.

### 3. Transform pipeline: exactly once (fixes A1)

One rule: **the stream loop owns per-record transforms** (preset → user transform → batch). The HTTP client applies transforms **only** when it received raw untransformed data, i.e. the `noBatch`/`executeSingleRequest` path.

- `addBatchToQueue` builds `requestConfig` with `transform: undefined, clone: false` — batch data is already transformed/cloned.
- `noBatch` path unchanged (http-client remains its single application site).
- Net effect: transform called exactly once per record on every path; `clone` costs one JSON roundtrip, not two.

### 4. Retry semantics: `0` means 0, `null` means fire-and-forget (fixes A3, A4)

- `RetryStrategy`: `this.maxRetries = options.maxRetries ?? 3`.
- `index.js` gets one resolver used by both http-client config builders:
  ```js
  const resolveRetries = (retries) => retries === null ? 0 : (retries ?? 3);
  ```
- `retries: null` → 1 attempt, no retry, no backoff (plus the existing `storeResponses: false` default). `retries: 0` → 1 attempt. `retries: 3` → up to 4 attempts (unchanged).
- `RetryError` message includes the last error: `All ${maxRetries} retry attempts failed: ${lastError.message}`.

### 5. Multipart: native FormData (fixes A5, drops `form-data` dep)

`FormDataHandler` rebuilt on the web `FormData`/`Blob` that native fetch understands:

- File paths → `fs.openAsBlob(path, {type})` when available (Node ≥19.8, streams lazily), else `new Blob([await readFile(path)], {type})` (Node 18 fallback).
- `form.append(key, blob, basename(path))`; buffers/streams in file objects wrapped in Blobs.
- The user's `Content-Type: multipart/form-data` header is **removed** before fetch so undici sets the real boundary. (Public behavior preserved: that header is how users request multipart mode.)
- `maxFileSize` validation, mime map, nested key flattening (`key[0]`, `key[nested]`) all keep current semantics.
- `isFilePath()` heuristic gains an `existsSync` check so string values containing `/` (e.g. `"application/json"`) are no longer misread as file paths.
- `createFormData` becomes async (internal signature only; not exported from package root).

### 6. Data input: `.json` files and `batchSize: 0` (fixes A2, B7)

- `.json` file path: `readFileSync` via the existing ESM `fs` imports (these are config-sized files; streaming parse is YAGNI — JSONL is the documented big-data path and stays streaming).
- `batchSize: 0` → `effectiveBatchSize = Infinity` → all records accumulate and ship as **one** request, matching README/CLI/type docs.
- `maxResponseBuffer: 0` → treated as "store nothing" (no CircularBuffer); `CircularBuffer` constructor throws on `maxSize < 1` so it can't corrupt silently again.

### 7. CLI + logger + stats polish (fixes B8, B9, B12–B15, C4)

- `cli.js`: package.json read via `new URL('./package.json', import.meta.url)`; `parse()` drops the `this.verbose` reference; `batch_size` default 2 → 1.
- Logger: all cursor manipulation behind `process.stdout.isTTY`; non-TTY runs get no progress bar (start/complete summaries still print). CI logs come out clean.
- `executeSingleRequest` measures real duration.
- `processMultipleConfigs` logs and returns the same stats object (`rowCount` = config count, consistently).
- `types.d.ts`: `verbose` documented default corrected to `false`.
- `sanitizeConfig` mask list adds `x-auth-token`, `api-key`, `x-access-token`, `proxy-authorization`.

### 8. Dependency + metadata cleanup (fixes B10, C2, C3)

Remove: `fetch-retry`, `readline`, `querystring` (use `node:querystring`), `json-stable-stringify`, `run-queue`, `form-data`.
Keep: `undici` (now real), `tough-cookie`, `dayjs`, `murmurhash`, `dotenv`, `ak-tools`, `yargs`.
`engines`: `>=18`. `build:cjs` externals list updated to match. README Node claim updated. Unused `StreamProcessors` methods pruned only if their unit tests are the sole references (low priority, last).

## Error handling strategy (unchanged, now enforced)

- Batch path: request errors → `errorCount++`, stored in response buffer (with statusCode/body) unless `errorHandler` supplied — exactly as today.
- Transform/preset errors: throw unless `errorHandler` supplied — as today.
- New failure surfaces (dispatcher, FormData) map onto existing error classes: connect failures → `NetworkError`, deadline → `TimeoutError`, oversized files → `ValidationError`.

## Testing strategy

1. **Regression-first:** every finding gets a test that fails on 2.0.16 (attempt counts, non-idempotent transform, `.json` input, real multipart round-trip, multi-`Set-Cookie`, socket reuse, `batchSize: 0`, CLI-from-tmpdir, non-TTY output).
2. **Socket-reuse proof:** local server counts TCP connections; N requests with pooling on ⇒ connections ≪ N; pooling off ⇒ connections ≈ N.
3. **Concurrency ceiling:** server tracks peak simultaneous requests; assert peak ≤ `concurrency` and (for wave-fix proof) that a slow request doesn't stall unrelated ones.
4. Full existing suite must stay green; the handful of tests that encode buggy behavior (if any surface) get corrected with a comment referencing the finding ID.
5. `npm run typecheck` + consumer type tests stay green.
6. Benchmarks: `npm run bench:100k` before/after on the same machine; record both in the PR. Expect wins from keep-alive reuse + wave elimination; no regression tolerated on memory benchmarks.

## Rollout

- Version `2.1.0` (behavior-fixes minor; the engines bump is documentation of an existing reality, called out in the changelog).
- Changelog enumerates each finding ID → fix.
- `npm run build` (CJS dist) + `npm test` + `npm run typecheck` green before publish.

## Risks

| Risk | Mitigation |
|---|---|
| Consumers depending on double-transform corruption | Vanishingly unlikely (it's corruption); changelog calls it out loudly. |
| Consumers depending on `retries: 0/null` actually retrying | Same — documented semantics win; changelog note. |
| `batchSize: 0` consumers relying on per-record sends | Possible but contradicts all docs; changelog note with migration hint (`batchSize: 1`). |
| undici Agent behavior differences vs default dispatcher | Socket-reuse + timeout tests pin the behavior; `pipelining: 1` matches fetch defaults. |
| Node 18.0–18.13 lacking `getSetCookie` | Feature-checked fallback to `headers.get('set-cookie')` single-cookie behavior (no worse than today). |
